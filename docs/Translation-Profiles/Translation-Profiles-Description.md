# Translation Profiles Module Description

## Module Name

Translation Profiles

## Purpose

Translation Profiles lets users save multiple provider-and-language setups under named labels and switch between them without re-entering credentials. Each profile is a snapshot of the provider, model, API key (or a reference to the system keychain), API base URL, source language, and target language. Users can create, rename, activate, and delete profiles from the Settings panel or the system tray menu. The active profile drives the current translation config, and profile changes persist immediately to `profiles.json`.

## Current Implementation

`TranslationProfilesStore` is the central data structure: a list of `TranslationProfile` records plus an `active_profile_id` string. At startup, `TranslationProfilesStore::load_with_issues()` reads `{config_dir}/aura-translation/profiles.json`. If the file is absent, a default store is written and returned. Parse or read failures are returned as startup issues while an empty store is used. `lib.rs` then emits those issues through the shared `daemon-error` event path and a background notification when no Aura window is visible.

`ensure_seeded_from_config()` runs once at startup after both the config and profiles are loaded. If the profiles list is empty, it creates a default profile from the current `AppConfig` and saves it. If the `active_profile_id` references a profile that no longer exists, it falls back to the first available profile and applies it to `AppConfig`. This guarantees that after startup, `AppConfig` always reflects the active profile's settings.

When the user saves new settings via `save_config`, `sync_active_profile_from_config()` updates the active profile's stored fields to mirror the freshly saved `AppConfig`. This keeps the stored profile snapshot current even when the user edits settings without explicitly creating a new profile.

Profile IDs are generated by `next_profile_id()`: a monotonic atomic counter combined with a millisecond timestamp, formatted as `"profile-{timestamp}-{sequence}"`. This avoids collisions even on rapid successive creates.

All write operations (`create_and_activate`, `rename`, `activate`, `delete`, `sync_active_profile_from_config`) call the private `TranslationProfilesStore::save()` immediately. Saves use the same write-then-rename atomic pattern as `config.json`.

### Capabilities

**Profile lifecycle**
- Create and activate a new profile from the current `AppConfig` state
- Rename an existing profile (validates that the name is non-empty)
- Activate a profile, applying its fields to `AppConfig` immediately
- Delete a profile; Aura enforces a minimum of one profile at all times
- When the active profile is deleted, the next profile in the list is automatically activated and applied

**Startup seeding**
- Auto-creates a `"Default"` profile if the profiles list is empty
- Restores `active_profile_id` to the first available profile if the stored ID is stale

**Active-profile sync**
- `sync_active_profile_from_config()` writes the current `AppConfig` fields back into the active profile after a settings save, keeping the snapshot current

**Tray menu integration**
- The tray's Profiles submenu is rebuilt from `TranslationProfilesStore` on every `save_config` and profile operation
- Each profile appears as a checked or unchecked menu item
- Clicking a tray profile item calls `activate_translation_profile` via the Tauri command

**Frontend display**
- `ProfileManager.svelte` lists all profiles with the active badge, provider/model/language summary, and Activate/Delete actions
- Delete shows a 5-second confirmation dialog before committing
- A name input plus "Save as new profile" and "Rename current profile" buttons drive create and rename flows

### Architecture

Service-layer pattern. The Rust `profiles.rs` module owns the `TranslationProfilesStore` data model, disk I/O, and all mutation methods. The `ProfilesState` managed state in `lib.rs` wraps the store in a `Mutex<TranslationProfilesStore>`. Tauri commands bridge CRUD operations to the frontend. The TypeScript side holds mirrored type definitions and the `ProfileManager.svelte` component provides the user interface.

### Rust Backend (`src-tauri/src/`)

- `profiles.rs`
  - `DEFAULT_PROFILE_ID`: `"default"` — the ID assigned to the auto-seeded first profile
  - `TranslationProfile`: serialisable struct with `id`, `name`, `api_key`, `api_key_storage`, `model`, `source_lang`, `target_lang`, `provider`, `api_base_url`, `available_models`
    - `from_config(id, name, config)`: snapshots the translatable fields from `AppConfig`; omits `api_key` when `api_key_storage` is `System`
    - `apply_to_config(config)`: writes all profile fields back into `AppConfig`, including `active_profile_id`
  - `TranslationProfilesStore`: `active_profile_id` + `Vec<TranslationProfile>`
    - `load_with_issues()`: reads `profiles.json` or returns an empty default plus startup issues
    - `ensure_seeded_from_config(config)`: seeds on empty or fixes a stale `active_profile_id`
    - `sync_active_profile_from_config(config)`: updates the active profile snapshot
    - `create_and_activate(name, config)`: validates non-empty name, generates a new ID, inserts at index 0, saves
    - `rename(profile_id, name)`: validates non-empty name, mutates in-place, saves
    - `activate(profile_id, config)`: applies the found profile to `AppConfig`, saves
    - `delete(profile_id, config)`: removes the profile; if it was active, activates the next remaining profile; rejects if fewer than 2 profiles remain
  - `next_profile_id()`: generates `"profile-{ms}-{counter}"` using `AtomicU64` + `SystemTime`
  - `profiles_path()`: `{config_dir}/aura-translation/profiles.json`

### Frontend (`ui/lib/`)

- `translationProfiles.ts`
  - `TranslationProfile`: TypeScript mirror of the Rust struct (all fields except `id` and `name` are shared with `AppConfig`)
  - `TranslationProfilesStore`: `{ active_profile_id: string; profiles: TranslationProfile[] }`

- `ProfileManager.svelte`
  - Accepts `store: TranslationProfilesStore | null`, `draftName: string`
  - Emits `oncreate`, `onrename(profileId)`, `onactivate(profileId)`, `ondelete(profileId)`, `ondraftnamechange(value)` callbacks
  - Shows the active profile badge next to the profile name
  - Displays provider, model, and language pair in monospace meta-line per profile
  - Delete confirmation guard: enters a 5-second timeout state before committing (`confirmingDeleteId` reactive variable); auto-cancels on timeout
  - Delete button disabled when `store.profiles.length <= 1`

### Integration Points

- `src-tauri/src/lib.rs`
  - `ProfilesState` (`Mutex<TranslationProfilesStore>`): managed Tauri state
  - Startup load issues from `TranslationProfilesStore::load_with_issues()` are emitted through `emit_daemon_error()` during `setup()`
  - `get_translation_profiles()`: returns a snapshot of the store
  - `create_translation_profile(config, name)`: calls `store.create_and_activate`, then `save_config` to sync the newly active profile into `AppConfig`
  - `rename_translation_profile(profile_id, name)`: calls `store.rename`
  - `activate_translation_profile(profile_id)`: calls `store.activate`, then rebuilds the tray profile submenu
  - `delete_translation_profile(profile_id)`: calls `store.delete`, then rebuilds the tray profile submenu
  - Tray profile submenu is rebuilt after every profile mutation using the updated `ProfilesState`

- `src-tauri/src/config.rs`
  - `AppConfig.active_profile_id`: synced from/to `TranslationProfile.id` on every activation
  - `AppConfig` provider/model/language fields are read by `TranslationProfile::from_config` and written back by `apply_to_config`

- `ui/lib/SettingsPanel.svelte`
  - Invokes `get_translation_profiles` on mount and after any profile mutation
  - Passes `store` and `draftName` to `ProfileManager`
  - Calls `invoke('create_translation_profile', ...)`, `invoke('rename_translation_profile', ...)`, `invoke('activate_translation_profile', ...)`, `invoke('delete_translation_profile', ...)` in response to `ProfileManager` events

## Current Limitations

- **Startup profile failures surface after Tauri setup begins**: load issues are emitted through `daemon-error`, but if no Aura window is visible the user may first see an OS notification before opening Settings.
- **No profile ordering control**: profiles are always inserted at index 0 on create; there is no user-facing drag-to-reorder capability.
- **Profile API keys are not independently managed in the keychain**: when a profile stores `api_key_storage: System`, the key is looked up under the provider's single system account (`"provider:deepseek"` etc.). Two profiles for the same provider cannot hold independent keys in the system store.
- **Profile deletion minimum is 1**: at least one profile must exist at all times. There is no way to reset to "no profiles" state.
- **No profile export or import**: profiles cannot be exported or shared between machines.

## Future Directions

- Add per-profile system keychain entries keyed by both provider and profile ID to support multiple keys for the same provider.
- Add profile import/export as JSON for cross-machine config sharing.
- Support user-controlled profile ordering via drag-to-reorder in the Settings panel.
- Add a "Duplicate profile" action as a convenience when creating a new profile that is similar to an existing one.
- Expose profile switching in the translation bubble (quick-access dropdown) in addition to the tray menu and Settings panel.
